### 1
эксперимент A
прогноз: до изменения 10 10, id совпадают. после a += 1: 11 10, у a новый id, id b прежний.
факт: совпал с прогнозом.

```
10 10
140711510328728 140711510328728
11 10
140711510328760 140711510328728
```

int - неизменяемый объект. a += 1 не меняет объект 10, а создаёт новый объект 11
и перепривязывает к нему имя a. b по-прежнему связано со старым объектом 10, поэтому его значение и id не изменились.

эксперимент B
прогноз: после append оба имени показывают [10, 20, 30], id совпадают.
после переназначения id разные, == True, is False, изменение нового списка на first не влияет.
факт: совпал с прогнозом.

```
  [10, 20] [10, 20]
  2280825868224 2280825868224
  [10, 20, 30] [10, 20, 30]
  2280825868224 2280825868224
  2280825868224 2280828089024
  first == second: True
  first is second: False
  [10, 20, 30] [10, 20, 30, 40]
```

second = first не создаёт новый список: оба имени связаны с одним объектом.
список изменяемый, append меняет этот объект на месте, поэтому изменение видно через оба имени.
second = [10, 20, 30] создаёт новый объект: значения равны (==), но объекты разные (is),
и изменения одного списка больше не влияют на другой.

схема до переназначения:
```
first  ──┐
         ├──► list [10, 20, 30]
second ──┘
```

схема после переназначения:
```
first  ──► list [10, 20, 30] 2280825868224
second ──► list [10, 20, 30] 2280828089024 (разные)
после second.append(40): second ──► [10, 20, 30, 40], first не изменился
```

вопросы:
1. нет. присваивание только привязывает ещё одно имя к тому же объекту, сам объект не меняется и не копируется.
2. неизменяемый объект нельзя поменять на месте, поэтому операция создаёт новый объект с результатом
   и привязывает имя к нему.
3. через is или сравнение id(). == для этого не подходит: он сравнивает значения, а не объекты.

alias = original - не копия, а второе имя для того же списка: id внешних списков совпадают,
поэтому alias видит все изменения.
original.copy() создаёт новый внешний список (свой id), но кладёт в него ссылки на те же вложенные списки
(id первого вложенного списка совпадает с original). поэтому append в original на shallow не влияет,
а изменение оценки внутри вложенного списка - влияет.
copy.deepcopy() копирует и внешний, и все вложенные списки, поэтому deep ни от чего не зависит.

расхождение: id первой оценки до изменения одинаковый у всех четырёх, даже у deep.
deepcopy не копирует неизменяемые объекты: число 5 нельзя изменить, поэтому копировать его незачем.
после original[0][1] = 3 элемент вложенного списка связывается с другим объектом (3),
поэтому id меняется у original, alias и shallow, а у deep остаётся прежним (5).

|---------------------|----------------------|----------------------------------------|-----------------------------------------------------------------------------|
| Присваивание        | нет                  | нет                                    | нет                                                                         |
| Поверхностная копия | да                   | нет                                    | частично: изменения внешнего списка независимы, изменения вложенных — общие |
| Глубокая копия      | да                   | да (кроме неизменяемых: строк и чисел) | да                                                                          |

матрицы
прогноз:
```

correct_matrix: только в первой строке.
```
факт: совпало.

```
wrong_matrix: [[1, 0, 0], [1, 0, 0], [1, 0, 0]]
строки - один объект: True
correct_matrix: [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
строки - один объект: False
```

[[0] * 3] * 3 создаёт одну строку [0, 0, 0] и кладёт во внешний список три ссылки на неё,
поэтому изменение через wrong_matrix[0] видно во всех строках (is даёт True).
в [[0] * 3 for _ in range(3)] выражение [0] * 3 выполняется три раза и создаёт три разные строки (is даёт False).

вопросы:
1. поверхностная копия создаёт только новый внешний объект, а вложенные объекты остаются общими с оригиналом.
глубокая копия рекурсивно копирует все вложенные изменяемые объекты.
2. глубокая копия дорогая: она проходит и копирует всю структуру, тратя время и память.
к тому же иногда объекты и должны оставаться общими, а некоторые объекты (например, открытые файлы) вообще нельзя скопировать.
3. когда элементы структуры неизменяемые (числа, строки) или когда меняется только сам внешний список
(добавление и удаление элементов), а вложенные объекты не трогаются.

### 3

счётчик ссылок
прогноз:
```
после создания 1, после alias 2, после контейнера 3, после del alias 2, после очистки 1.
```
факт: ответ на 1 больше, так как при подсчёте создаётся временная ссылка, которая тоже учитывается.

```
После создания: 2
После создания alias: 3
После помещения в контейнер: 4
После del alias: 3
После очистки контейнера: 2
```

sys.getrefcount() показывает на одну ссылку больше: при вызове объект передаётся в функцию как аргумент,
и эта временная ссылка тоже входит в счёт. после завершения вызова она исчезает.

увеличивают счётчик: новое имя (alias = data), помещение в контейнер ([data]), передача в функцию.
уменьшают: del имени, удаление из контейнера (clear()), переназначение имени на другой объект.

del alias удаляет только имя alias, а не объект. объект удаляется сам, когда его счётчик падает до 0,
а пока на него ссылаются data и container, он продолжает существовать.

слабая ссылка
прогноз:
```
первый print выведет объект Record, после del record - None.
```
факт: совпал.

```
<__main__.Record object at 0x0000023E2237BA10>
None
```

слабая ссылка не увеличивает счётчик ссылок, поэтому не удерживает объект в памяти.
после del record сильных ссылок не осталось, объект удалился, и weak_record() вернул None.

где полезны слабые ссылки: кэш. например, программа запоминает загруженные картинки, чтобы не загружать их повторно.
обычный словарь держит их сильными ссылками, и картинки не удалятся никогда, даже когда больше не нужны - память только растёт.
словарь со слабыми ссылками хранит картинку, пока она где-то используется, а потом она удаляется сама,
и не нужно вручную помнить, когда её убрать из кэша.

практическая задача
прогноз:
```
сначала в реестре first, second, third. после del temp - first, second. после del second - только first.
```
факт: совпал.

```
=== Слабый реестр ===
Сначала в реестре: ['first', 'second', 'third']
После del temp: ['first', 'second']
После del second: ['first']
```

WeakValueDictionary хранит объекты слабыми ссылками. у каждого объекта была одна сильная ссылка - имя.
после del temp и del second на эти объекты не осталось сильных ссылок, они удалились и сами пропали из реестра.
реестр не управляет временем жизни объектов: объект в нём, пока его держит кто-то другой.

вопросы:
1. когда счётчик ссылок падает до нуля: ни одно имя, контейнер или другой объект на него больше не ссылается.
2. нет. CPython обычно оставляет освободившуюся память у себя и использует её под новые объекты,
   а не возвращает операционной системе сразу.
3. сильная ссылка увеличивает счётчик и удерживает объект в памяти. слабая - не увеличивает
   и не мешает удалению; когда объект удалён, она возвращает None.


### 4
цикл и сборщик
прогноз:
```
обе проверки цикла - True. сборщик включён - True.
пороги - три числа, по одному на поколение. статистика - три словаря.
```
факт: совпал.

```
first ссылается на second: True
second ссылается на first: True

=== Сборщик мусора ===
Автоматический сборщик включён: True
Пороги поколений: (2000, 10, 10)
Статистика поколений:
  поколение 0: {'collections': 4, 'collected': 139, 'uncollectable': 0}
  поколение 1: {'collections': 0, 'collected': 0, 'uncollectable': 0}
  поколение 2: {'collections': 0, 'collected': 0, 'uncollectable': 0}
```

в поколении 0 уже были сборки, хотя программа почти ничего не делала:
это мусор, оставшийся после запуска интерпретатора и загрузки его модулей.

удаление цикла
прогноз:
```
после del first, second оба списка останутся в памяти, gc.collect() соберёт 2 объекта.
```
факт: совпал.

```
=== Удаление цикла ===
id first: 2572556220096
id second: 2572556095424
gc.collect() собрал объектов: 2
```

перед удалением сделан отдельный gc.collect(), чтобы убрать посторонний мусор и замерить только наш цикл.
одного подсчёта ссылок недостаточно: после del first, second у каждого списка остаётся ссылка от соседа,
счётчики равны 1, а не 0, поэтому сами они не удалятся. при этом из программы до них уже не добраться.
найти и удалить такие группы может только циклический сборщик мусора.

поколения: большинство объектов живёт недолго, а прожившие долго, скорее всего, проживут и дальше.
поэтому сборщик делит объекты по возрасту: новые проверяет часто, а пережившие проверки - всё реже.
так он не тратит время на постоянную проверку всех объектов программы.

сборщик выключен
прогноз:
```
пока сборщик выключен, циклы будут копиться. gc.collect() соберёт все 10 списков (5 пар).
```
факт: совпал.

```
=== Сборщик выключен ===
Автоматический сборщик включён: False
Объектов в поколении 0 до сборки: 10
gc.collect() собрал объектов: 10
Автоматический сборщик включён: True
```

на каждом шаге цикла имена a и b переходили к новой паре, а старая пара оставалась в памяти:
её списки держат друг друга. за 5 шагов накопилось 10 списков, все собраны одним ручным вызовом.
без append (без циклов) старые списки удалялись бы сразу подсчётом ссылок, и собирать было бы нечего.
автоматическая сборка после эксперимента восстановлена через gc.enable().

практическая задача
прогноз:
```
до создания графа собирать нечего - 0. после удаления A, B, C соберутся все их объекты, D останется доступен.
```
факт: совпал, собрано 6 объектов.

```
=== Граф ===
Собрано до создания графа: 0
A -> ['B']
B -> ['C']
C -> ['A']
D -> []
Собрано после удаления графа: 6
Независимый узел доступен: {'name': 'D', 'links': []}
```

схема графа:
```
A ──► B ──► C          D
▲           │
└───────────┘
```

каждый узел - словарь с именем и списком links. связи в коде:
node_a["links"].append(node_b) - стрелка A → B, node_b["links"].append(node_c) - B → C,
node_c["links"].append(node_a) - C → A. у D список links пуст, на него никто не ссылается.

собрано 6, а не 3: каждый узел - два объекта, словарь и список links внутри него.
D не собран: на него ссылается имя node_d, assert это подтверждает.

вопросы:
1. когда объекты прямо или через цепочку ссылаются друг на друга: a ссылается на b, а b на a.
2. в цикле объекты держат друг друга, поэтому счётчик каждого больше нуля,
   но ни одного внешнего имени на них нет, и из программы до них не добраться.
3. чтобы не проверять все объекты каждый раз: новые объекты чаще становятся мусором, их проверяют часто,
   а долгоживущие - редко. так сборка мусора занимает меньше времени.

### 5
часть 1. размеры объектов
прогноз:
```
пустой список займёт несколько десятков байт, а не 0 - у любого объекта есть служебные данные.
список из 10 чисел будет больше пустого на 10 ссылок, кортеж - чуть меньше списка.
None займёт меньше всех.
```
факт: совпал.

```
=== Часть 1. Размеры объектов ===
Пустой список: 56
Список из 10 чисел: 136
Кортеж из 10 чисел: 128
Строка из 10 символов: 51
Целое число: 28
None: 16
```

размер контейнера не включает объекты, на которые он ссылается: список хранит только ссылки, по 8 байт каждая.
56 (пустой список) + 10 × 8 (ссылки) = 136. сами числа в эти 136 байт не входят:
список из трёх огромных чисел весит столько же, сколько список из трёх нулей.
кортеж меньше списка: он никогда не растёт, и ему не нужно хранить данные о зарезервированном месте.
даже у None есть 16 байт служебных данных - в Python всё является объектом.

часть 2. рост списка
прогноз:
```
размер будет расти не после каждого append, а скачками.
```
факт: совпал.

```
=== Часть 2. Рост списка ===
длина 0: 56 байт
длина 1: 88 байт
длина 5: 120 байт
длина 9: 184 байт
длина 17: 248 байт
длина 25: 312 байт
длина 33: 376 байт
длина 41: 472 байт
длина 53: 568 байт
длина 65: 664 байт
длина 77: 792 байт
длина 93: 920 байт
```

размер увеличивается не после каждого append: при первом добавлении список сразу резервирует место под 4 элемента
((88 - 56) / 8 = 4), следующие три ложатся в готовые ячейки.
запас нужен, потому что ссылки хранятся одним сплошным куском памяти: когда место кончается, список выделяет
новый кусок и копирует туда все ссылки. если делать это на каждом append, добавление было бы очень медленным.
длина (len) - сколько элементов в списке сейчас, а выделенная память - сколько ячеек зарезервировано,
включая пустые. например, при длине 5 размер 120 байт: 8 ячеек, из которых заняты 5.

часть 3. tracemalloc
прогноз:
```
список займёт несколько мегабайт, range - почти ничего.
```
факт: совпал.

```
=== Часть 3. tracemalloc ===
list(range(100_000)): текущий 3897.2 КБ, пиковый 3897.2 КБ
range(100_000): текущий 0.0 КБ, пиковый 0.0 КБ
```

getsizeof такого списка - около 800 КБ (100 000 ссылок по 8 байт), а tracemalloc показал почти 3,9 МБ:
он учитывает всё, что выделено за время записи, включая 100 000 объектов-чисел.
range не хранит числа: он помнит только начало, конец и шаг и выдаёт значения по требованию.
вывод: материализованная последовательность (список) хранит все значения сразу и занимает память пропорционально их числу,
а объект с правилом (range) занимает одинаково мало при любом количестве значений.

практическая задача
```
=== Размеры объектов ===
пустой список: элементов 0, размер 56 байт
список из 10 чисел: элементов 10, размер 136 байт
кортеж из 10 чисел: элементов 10, размер 128 байт
строка из 10 символов: элементов 10, размер 51 байт
целое число: элементов -, размер 28 байт
None: элементов -, размер 16 байт

=== Список против range ===

Сценарий: list(range(100_000))
Элементов: 100000
Размер внешнего объекта: 800056 байт
Текущий объём: 3897.8 КБ
Пиковый объём: 3897.8 КБ

Сценарий: range(100_000)
Элементов: 100000
Размер внешнего объекта: 48 байт
Текущий объём: 0.0 КБ
Пиковый объём: 0.0 КБ

Отношение пиков list / range: 124731
```

результаты сначала сохраняются в списки словарей (sizes и results), и только потом выводятся.
пик range - около 32 байт (3897,8 × 1024 / 124731), поэтому после округления до КБ получается 0.0.
он настолько мал, что в некоторых запусках бывает ровно 0, поэтому перед делением стоит проверка,
иначе программа упала бы с ZeroDivisionError.

итоговый анализ: как уменьшить лишнее потребление памяти
1. использовать объекты с правилом вместо готовых списков (range, генераторы), если значения нужны по одному -
   часть 3: range(100_000) занимает десятки байт вместо почти 4 МБ у списка.
2. хранить неизменяемые данные в кортежах, а не в списках - части 1 и 2: кортеж меньше списка
   и не резервирует место под рост.
3. не копировать без необходимости и не применять deepcopy «на всякий случай» - задание 2:
   глубокая копия дублирует всю структуру, а поверхностной часто достаточно.
4. не держать лишних сильных ссылок: удалять ненужные большие объекты, а кэши и реестры строить на слабых ссылках -
   задание 3: WeakValueDictionary не удерживает объекты, и они освобождаются сами.

итоговый вывод
самые опасные ошибки с изменяемыми объектами - те, что не вызывают ошибки, а тихо портят данные:
1. b = a вместо копии: оба имени указывают на один объект, и изменение через одно видно через другое (задание 1).
2. .copy() для вложенной структуры: вложенные списки остаются общими с оригиналом (задание 2).
3. [[0] * 3] * 3: три ссылки на одну строку, изменение одной «строки» меняет все (задание 2).
4. забытая ссылка, которая держит объект: переменная цикла или обычный кэш не дают объекту удалиться,
   и память утекает (задания 3 и 4).
проверить, общий ли объект, можно через is или id(); == для этого не подходит, он сравнивает только значения.
